## ① 파비콘 — 가지 모양

**지금 상태 (확인함)**

```
GET /favicon.ico  →  200  ·  Content-Type: text/html  ·  1291 bytes
```

`index.html`이 그대로 온다. `vercel.json`의 SPA 폴백이 **모든 경로를 `index.html`로 보내기
때문에** 없는 파비콘 요청까지 가로챈다. 브라우저 탭에는 기본 지구본이 뜬다.

`index.html`의 `<head>`에도 `<link rel="icon">`이 없고, `public/` 폴더 자체가 없다.

**할 일**

1. `public/` 폴더를 만들고 **`favicon.svg`** 를 넣는다.
   - **`src/shared/ui/brandMark.tsx`의 가지 SVG를 그대로 쓴다.** 이미 직접 그려 둔 것이 있다
     (열매 `#7C3AED` + 꼭지 `#16A34A`). 새로 그릴 이유가 없고, **표식이 두 벌이 되면
     화면과 탭이 서로 다른 가지를 그리게 된다.**
   - 탭 아이콘은 16~32px로 줄어든다. 24px 뷰박스 그대로면 꼭지가 뭉개질 수 있으니
     **줄여 놓고 눈으로 확인**한다. 필요하면 파비콘용으로 선을 굵게 잡는다.
2. `index.html`에 링크를 건다.
   ```html
   <link rel="icon" type="image/svg+xml" href="/favicon.svg" />
   ```
3. **`favicon.ico`도 함께 둔다.** SVG 파비콘을 못 읽는 환경이 남아 있고, 무엇보다
   **브라우저는 링크가 없어도 `/favicon.ico`를 찔러 본다** — 지금처럼 HTML이 응답하는 것보다
   진짜 아이콘이 오는 편이 낫다.
4. **`vercel.json` 확인.** `public/`에 실제 파일이 생기면 Vercel은 정적 파일을 rewrite보다
   먼저 매칭하므로 설정을 안 고쳐도 된다 — **다만 배포 후 `Content-Type`이 실제로
   `image/svg+xml`로 바뀌는지 반드시 확인한다.** 안 바뀌면 rewrite에서 제외 규칙을 더한다.

**확인 방법**

```
curl -sI <배포주소>/favicon.svg   →  Content-Type: image/svg+xml
curl -sI <배포주소>/favicon.ico   →  Content-Type: image/x-icon  (text/html이면 실패)
```
탭에서 눈으로도 본다. 라이트/다크 양쪽에서 가지가 보이는지까지.

## ② 채팅 사진 고아 버그 (`backlog.md` §1-3)

어제 탈퇴 검증에서 **재현 조건까지 확인한 실제 버그**다.

**기전**

```
탈퇴 ②   방 주인이 사라짐 → chat_rooms 행이 cascade로 삭제
탈퇴 ③   사진 올린 본인
           fetchRoomIds() → 방이 이미 없어 빈 배열
           → `{방번호}/{본인}` 경로를 훑지 못함 → 파일이 남는다
```

지울 경로를 아는 **유일한 근거가 `chat_rooms` 행**인데, 그 행이 **남의 탈퇴에 딸려 먼저**
사라진다. 0031이 미뤄 둔 "상대가 올린 사진이 남는다"보다 한 겹 더 나쁘다 —
**자기 사진인데도** 못 지운다.

**급하지 않은 이유**: `chat_images_select`가 "그 방이 있고 내가 참여자일 것"을 요구해
**아무도 못 읽는다.** 용량만 차지한다.

**고치는 길**

`supabase/functions/delete-account/index.ts`의 `removeUserFiles`를 고친다.
방 기록에 기대는 지금 방식 대신, **`chat-images` 버킷의 최상위 폴더를 훑어
`{폴더}/{내id}/`를 지운다.**

- `storage.list('')`로 방 번호 폴더 목록을 받고, 각 폴더에서 `{방}/{내id}`를 `list`한다.
- 지금 방식(방 기록 기반)을 **없애지 말고 남겨 둔다.** 그쪽이 훨씬 싸고, 대부분의 탈퇴는
  방이 살아 있는 상태에서 일어난다. 버킷 훑기는 **못 찾은 나머지를 줍는 두 번째 그물**이다.
- 방 수가 많아지면 list 호출이 늘어난다. `LIST_PAGE_SIZE`(100) 페이징이 이미 있으니
  그대로 쓰고, **상한을 넘으면 조용히 멈추는 지금 태도를 유지한다** — 뒷정리가 실패해도
  탈퇴 자체는 성공해야 한다.

**정책은 손대지 않는다.** `chat_images_delete`에 **이미 `방이 없으면 삭제 허용` 조항이
있다**(0032). 만든 사람이 이 경우를 예상은 했던 자리라, 함수만 고치면 된다.

**배포**: `supabase functions deploy delete-account` (v3). 배포 후 로그에서 200 확인.

## ③ 같은 모양의 엣지케이스 전부 훑기

②는 **"정리 코드가 근거로 삼는 행이 먼저 사라진다"** 는 모양의 버그다.
스토리지 뒷정리 경로가 여섯 군데 더 있는데 **전부 한 번도 검증된 적이 없다.**
구현은 되어 있으니 확인만 하면 된다.

| # | 경로 | 구현 위치 | 상태 |
|---|---|---|---|
| 1 | 프로필 사진 **교체** → 옛 파일 삭제 | `profileApi.removeAvatarObject` | 구현됨 · 미검증 |
| 2 | 프로필 사진 **삭제**(`removeAvatar`) | 〃 | 구현됨 · 미검증 |
| 3 | 게시물 수정으로 사진 **교체·삭제** | `postApi.removePostImageFiles` | 구현됨 · 미검증 |
| 4 | 게시물 **삭제** → 사진 + 그 글의 채팅 사진 | `postApi.deletePost` + `0032` | 구현됨 · 미검증 |
| 5 | 채팅방 **나가기** → 양쪽 다 나가면 purge | `purge_chat_room` + `0031` | 구현됨 · 미검증 |
| 6 | 업로드 **중간 실패** → 보상 삭제 | `postApi.removeUploadedImages` | 구현됨 · 미검증 |

**4번은 순서를 미리 확인해 두었다 — 문제없다.** `deletePost`가 지우기 **전에** 경로를 읽는다.

```ts
const urls = (await fetchPostImageRows(postId)).map(…);
const chatImagePaths = await listPostChatImagePaths(postId, sellerId);
await supabase.from('posts').delete().eq('id', postId);   // ← 읽은 뒤에 지운다
await removePostImageFiles(urls);
await removeChatImages(chatImagePaths);
```

②가 깨진 것이 바로 이 순서 때문이었는데, 여기는 제대로 되어 있다. 그래도 **끝까지 밟아 본
적은 없으니** 검증 대상에 남긴다.

**5번이 ②와 같은 눈으로 볼 자리다.** 채팅방 나가기는 `purge_chat_room`이 방 행을 지우는데,
**그 행이 사라진 뒤에 사진을 지울 수 있는가**가 ②와 똑같은 질문이다. 여기부터 본다.

**어떻게 검증하나**

통합 테스트로 덮을 수 있는 것과 아닌 것이 갈린다.

- **트리거·제약·cascade** → `*.int.test.ts`로 덮인다. 픽스처가 이미 있다
  (`shared/testUtils/integration/fixtures.ts`).
- **스토리지 정리** → 서비스 키로 파일을 넣고, 동작시키고, `storage.objects`를 다시 세면
  된다. **지금 통합 테스트에 스토리지를 만지는 것이 하나도 없으니 여기서 처음 연다.**
- **로그인한 사용자로서의 RLS** → 여전히 못 닿는다(Email 프로바이더를 꺼서 세션을 못 만든다).
  4·5번은 화면에서 사람이 밟아야 하는 부분이 남는다.

각 항목마다 **"고쳤으면 반드시 테스트"** 규칙을 지킨다.

## ⑤ 링크 공유용 메타 태그 (추가 제안)

`index.html`의 `<head>`에 `charset`·`viewport`뿐이다(확인함). 지금 카카오톡이나 슬랙에
주소를 붙이면 **제목도 설명도 썸네일도 안 나온다.**

```html
<meta name="description" content="…" />
<meta property="og:title" content="가지마켓" />
<meta property="og:description" content="…" />
<meta property="og:image" content="/og-image.png" />
<meta property="og:url" content="https://eggplant-market-ga6d-flame.vercel.app" />
```

**중고거래 앱이라 링크 공유가 실제 사용 경로다.** 파비콘(①)과 같은 작업 묶음으로 하면
`public/` 폴더를 한 번만 만들면 된다.

> 게시물별 og 태그는 **하지 않는다.** SPA라 서버가 HTML을 만들지 않아서 글마다 다른
> 메타를 넣으려면 SSR이나 Edge Function 프리렌더가 필요하다 — 무게가 다른 일이다.

## ⑥ Vercel Preview 배포에서 로그인이 막힌다 (추가 제안 · 판단 필요)

Preview 배포는 **PR마다 주소가 달라진다**(`eggplant-market-git-<브랜치>-….vercel.app`).
Supabase Redirect URLs에는 프로덕션 주소만 넣었으므로 **Preview에서는 소셜 로그인이
돌아오지 못한다.**

두 갈래이고 **판단이 필요하다.**

- **와일드카드를 등록한다** — Supabase Redirect URLs는 `https://*-<계정>.vercel.app/**`
  같은 패턴을 받는다. 편하지만 **그 계정의 모든 Vercel 배포가 복귀 지점이 된다.**
- **그냥 둔다** — Preview에서는 로그인을 안 쓴다고 정하고, 확인은 로컬과 프로덕션에서만 한다.

지금은 혼자 쓰는 저장소라 **후자로 충분해 보인다.** 다만 "Preview에서 로그인이 안 되는 것은
설정 누락이 아니라 결정"이라고 적어 두어야 다음에 같은 자리에서 헤매지 않는다.

## ⑦ 업로드 크기 상한 재검토 (추가 제안 · 작음)

`MAX_POST_IMAGE_BYTES`가 5MB인데, 이제 **올리기 전에 줄인다**(어제 작업, 4MB → 483kB 실측).
그래서 **원본이 커도 실제 저장량은 작다.** 고화소 폰 사진은 5MB를 넘는 일이 있어서
지금은 **줄일 수 있는 사진을 미리 거절**하고 있다.

상한을 10~12MB로 올리는 것을 검토한다. 검증 상수와 그 테스트를 함께 고쳐야 한다.
**축소가 실패하면 원본이 그대로 올라간다는 점**을 잊지 않는다 — 상한을 올리면
그 최악의 경우도 함께 커진다.
